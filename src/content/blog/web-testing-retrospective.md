比赛结束后回头看，最难受的不是“不会做”，而是明明每个知识点都见过，真正上手时却一直在原地打转。这篇复盘不记流水账，只回答两个问题：为什么实现速度慢，为什么最终效果差。

## 先说结论

慢，主要不是代码写得慢，而是**在错误的地方反复试错**：定位元素、调等待、重跑失败用例，把时间吃掉了。

效果差，主要不是用例数量不够，而是**用例设计后置、断言太浅、失败不可诊断**：脚本跑完了，但没有真正验证业务。

## 一、为什么慢

### 1. 跳过用例设计，直接写脚本

拿到赛题后第一反应是打开 IDE 写 `driver.find_element`，边看页面边补步骤。结果是：

- 写到一半发现前置条件没定义，只能推倒重来；
- 用例之间互相依赖，登录态、测试数据反复处理；
- 覆盖全凭感觉，简单页面写了很多，核心流程反而漏了。

用例设计不是“额外工作”，它决定了脚本的结构。没有用例，脚本就只是一串操作记录。

### 2. 把“能跑”当成“验证过”

早期为了尽快看到绿色，断言写得很轻：页面标题对、URL 对、元素存在，就算通过。这样的用例跑得再快，也发现不了业务错误。更糟的是，它给了虚假的安全感，让人误以为进度不错。

### 3. 等待策略靠 `sleep` 和重试

页面是动态渲染的，元素没出来就操作，报错后再加 `time.sleep`，不行就加大数值。单个用例看似稳定了，整体执行时间被拖长，而且换台机器、换个网络就又不稳定。

正确的做法是显式等待具体条件，而不是等一个固定时长。这一点赛前知道，赛中却没形成肌肉记忆。

### 4. 元素定位靠猜和复制

用浏览器开发者工具临时找一个 XPath，复制到脚本里，能跑就不管了。赛题页面稍一变化，或者列表渲染顺序不同，定位立刻失效。定位策略没有分层，也没有统一封装，改一个选择器要翻遍整个文件。

### 5. 遇到阻塞不及时绕行

某个用例因为环境、弹窗或数据问题一直失败，就反复重跑、反复调试。比赛时间有限，一个点卡住，后面的用例就没有时间写。事后看，当时最正确的动作是记录问题、标记跳过，先把能拿的分拿到。

### 6. 环境和工具链问题留到赛中暴露

浏览器驱动、依赖版本、Python 环境、截图目录，这些在平时都应该是一次性配置好的东西。赛中才处理，等于用比赛时间做环境搭建。

## 二、为什么效果差

### 1. 覆盖结构失衡

没有用例清单，就没有优先级。结果往往是：页面能点的地方都点了一遍，但注册、登录、下单这类主链路只覆盖了表面。

### 2. 断言只停留在页面层

“元素可见”“跳转成功”只能证明页面有反应，不能证明业务正确。缺少对关键字段、状态变化、数据结果的校验，用例的含金量很低。

### 3. 测试数据没有隔离

用例共用同一份数据，前一个用例改了状态，后一个用例就失败。失败后又很难判断是产品问题还是数据问题。

### 4. 失败不可诊断

失败时只有一行 `NoSuchElementException`，没有截图、没有页面源码、没有当前 URL 和关键日志。每次定位问题都要重新复现，调试成本极高。

## 三、时间到底去哪了

按实际感受排序，大致是这样：

| 时间去向 | 占比感受 | 是否直接产出分数 |
| --- | --- | --- |
| 定位元素、调等待 | 最高 | 低 |
| 失败后重跑、反复调试 | 高 | 低 |
| 环境与依赖问题 | 中 | 无 |
| 用例设计与断言思考 | 低 | 高 |

问题很清楚：大量时间花在了不直接产生分数的环节，而真正决定质量的用例设计和断言，反而被压缩了。

## 四、如果重来一次

### 1. 先写用例，再写脚本

拿到赛题后的第一件事不是打开 IDE，而是列一张用例表：

- 用例编号、模块、前置条件
- 操作步骤、预期结果
- 优先级：P0 主链路、P1 重要分支、P2 边界
- 是否依赖登录态或特定数据

这张表决定了脚本目录、fixture 和执行顺序。用例没定，不要开始写代码。

### 2. 先跑通一条主链路

不要一上来铺开所有模块。先选一条最核心的链路，把登录、页面操作、断言、截图完整跑通，形成可复制的骨架，再按用例表扩展。这样能最早暴露环境和框架问题。

### 3. 统一等待与定位封装

所有等待走显式等待，封装成工具函数：

```python
from selenium.webdriver.support.ui import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC


def wait_visible(driver, locator, timeout=10):
    return WebDriverWait(driver, timeout).until(
        EC.visibility_of_element_located(locator)
    )
```

定位优先级固定为：`data-testid` → `id` → `name` → CSS → XPath。XPath 只作为最后手段，并且尽量基于稳定的文本或属性，不依赖层级。

### 4. 断言分层

每个 P0 用例至少覆盖两层：

1. 页面层：URL、标题、关键元素状态；
2. 业务层：关键字段值、列表条数、状态文案、数据变化。

只有页面层断言的用例，不能算完成。

### 5. 阻塞十分钟就绕行

给自己定一条硬规则：同一个问题超过十分钟没有进展，立刻记录现象、标记跳过，继续做后面的用例。比赛结束后再复盘，而不是在赛中死磕。

### 6. 失败必须留下证据

统一在失败时保存：

- 当前 URL 和页面标题
- 截图
- 关键元素文本或页面源码片段
- 用例入参和前置状态

这样定位问题不需要重新复现，调试时间会大幅下降。

### 7. 时间盒

把比赛时间切成明确阶段：

- 前段：读题、列用例、确认环境
- 中段：跑通主链路，搭好骨架
- 后段：按优先级批量补用例
- 末段：回归、修稳定性、整理提交物

每个阶段结束检查一次进度，发现偏离就砍需求，保 P0。

## 五、赛后要补的能力

- **Selenium 4 的等待与相对定位**：显式等待、`expected_conditions`、稳定的定位策略。
- **Pytest 的组织能力**：fixture 管理登录态、参数化覆盖边界、失败重试与报告。
- **用例设计**：等价类、边界值、状态迁移，先保证覆盖结构正确。
- **调试方法**：从“改代码试”转为“看日志、看截图、缩小范围”。

## 小结

这次比赛最大的教训，不是某个 API 不熟，而是**把实现放在了设计前面，把能跑当成了验证**。速度慢和效果差，其实是同一个问题的两面：没有用例设计，脚本就没有方向；没有有效断言，跑通也没有意义。

下次再上场，先花时间把用例表写清楚，再让代码去执行它。慢一点开始，反而会快很多。
